# CS2 Local Tournaments

Сайт для локальных турниров по CS2 среди друзей: сетка на выбывание для
команд 2×2, встроенные пики/баны карт и призовой фонд.

Бэкенд — FastAPI + Postgres (локально SQLite). Фронтенд — React + Vite. У каждого участника
свой аккаунт и личный кабинет; аккаунты заводит администратор.

## Деплой

Сайт живёт на Vercel (бесплатный тариф Hobby): https://cs2-tournament-virid.vercel.app

- Фронт — статика из `frontend/dist`, весь бэкенд — одна Python-функция
  `api/index.py` (см. `vercel.json`), фронт и `/api` на одном домене.
- База — Neon Postgres (Free), подключена к проекту через Vercel Marketplace
  и сама кладёт `DATABASE_URL` в переменные окружения. Функция стоит в том же
  регионе, что и база (`iad1`).
- Ещё нужны `SECRET_KEY`, `ADMIN_USERNAME`, `ADMIN_PASSWORD` — заданы в
  настройках проекта на Vercel.

Репозиторий https://github.com/vertigoDK/cs2-tournament подключён к Vercel:
**каждый пуш в `main` сам выкатывается на сайт**, а на каждую ветку и PR
Vercel собирает превью со своей ссылкой.

Осторожно: превью работают с той же боевой базой, что и сайт. Что сделано в
превью (создали турнир, сбросили результат) — то сделано и на проде.

Страница турнира подтягивает состояние сетки сама: раз в 5 секунд обычно и
раз в 2 секунды пока идёт драфт карт — зрители и капитаны видят ходы без F5.

## Роли и доступ

| Роль    | Как появляется                        | Права |
|---------|---------------------------------------|-------|
| admin   | создаётся сам из `.env`               | участники, турниры, сетка, результаты, пики/баны |
| участник| заводит админ на странице «Участники»  | свой личный кабинет, просмотр турниров и сеток |

Общего гостевого аккаунта больше нет — у каждого свой вход.

Админ добавляет человека по нику, система выдаёт **случайные логин и
пароль и показывает их один раз**. Входить можно как по выданному логину,
так и по нику — регистр не важен. В списке участников под ником показан
**логин**; пароль там не отображается никогда. У кого пароль ни разу не
показывали (например, у перенесённых со старой схемы) стоит пометка
«нет пароля» — им нужно нажать «Выдать пароль». Ники уникальны без учёта регистра и
пробелов по краям, так что «Patrick» и «patrick» занять одновременно нельзя. Дальше пароль хранится только хэшем:
посмотреть его нельзя, но админ может выдать новый кнопкой «Новый пароль».

Пароль администратора задаётся переменной `ADMIN_PASSWORD` и применяется
только при первом запуске на пустой базе.

## Функциональность v1

- **Участник = аккаунт**: один список людей, который переиспользуется между
  турнирами. Личный кабинет (`/me`): ник, аватар (своё фото или цветная
  подложка с инициалом), статистика, следующий матч и история матчей.
  Фото участник загружает себе сам — админ для этого не нужен.
- **Название и логотип команды** — необязательные. Если не задать, команда
  зовётся «ник + ник», а вместо логотипа показываются аватарки обоих игроков.
- Создание турнира: название, призовой фонд, команды 2×2 собираются выбором
  двух участников из списка (один человек не может быть в двух командах сразу),
  режим посева (по порядку добавления / парами подряд / случайно).
- Автогенерация сетки на выбывание (bye для непарного числа команд).
- Клик по команде в карточке матча — назначить победителя; повторный клик
  снимает результат вместе со всей веткой ниже.
- **Дата и время начала турнира**: админ всегда вводит его по времени
  Алматы/Астаны (UTC+5), независимо от своего часового пояса. У любого
  зрителя (например, по Москве) время и живой обратный отсчёт до старта
  автоматически пересчитываются в его локальный часовой пояс правильно.
- **Капитаны и живой драфт карт.** В каждой команде админ назначает
  капитана (звёздочка у ника при сборе состава). Админ открывает драфт на
  карточке матча — дальше карты по очереди выбирают сами капитаны, каждый
  со своего аккаунта, и видят ходы друг друга почти сразу: пока драфт идёт,
  страница опрашивает сервер раз в 2 секунды вместо 5.
  Право хода проверяет бэкенд, а не интерфейс: чужой капитан и не-капитан
  получают отказ. Админ может походить за любого, если капитан не в сети.
  Драфт недоступен, пока турнир не начат.
  Формат серии задаётся при создании турнира: **BO1** (четыре бана →
  решающая карта) или **BO3** (бан, бан, пик, пик → решающая карта).
  Бан подсвечен красным, пик — зелёным.
- **Счёт по картам.** После драфта у матча появляются карты серии; админ
  отмечает победителя каждой. Итог матча считается сам (BO3 — до двух
  побед) и проход по сетке обновляется; откат результата карты снимает
  и проход. В карточке матча видно счёт и кто какую карту взял.
- **Статистика** (`/stats`) — три вкладки:
  *Игроки* — таблица с K/D/A, K/D, KDA, килами в раунде (KPR), победами на
  картах и титулами; сортируется по любому показателю.
  *Карты* — сколько раз каждую пикали, банили и играли.
  *История* — прошедшие турниры со всеми матчами: кто кого прошёл, какие
  карты сыграны, с каким счётом и кто их пикнул.
  На главной остаётся только текущий турнир.
- **Статистика карты вносится админом вручную** после игры: кнопка
  «Статистика» у карты в драфте открывает форму — счёт по раундам и K/D/A
  на четверых, с подсчётом KDA на лету. Победитель карты определяется по
  счёту раундов. Верхней границы у счёта нет — овертаймы вроде 19:17
  вносятся как есть; при равном счёте победителя можно указать вручную.
- **Принудительный старт**: кнопка «Начать турнир» запускает его раньше
  объявленного времени — отсчёт останавливается, открывается драфт.
  Есть обратное действие и сброс результатов.

## Структура

```
api/        точка входа Vercel
backend/    FastAPI-приложение (app/), локальная SQLite в data/
frontend/   React + Vite SPA
  public/maps/   картинки карт для драфта
```

### Загруженные картинки

Аватарки и логотипы хранятся прямо в базе (таблица `images`): постоянного
диска у Vercel нет. При загрузке картинка ужимается до 256px и пересохраняется
в PNG — это отсекает мегабайтные скриншоты и заодно выбрасывает из файла всё
постороннее. Ограничение на исходный файл — 4 МБ (Vercel не пропускает тело
запроса больше 4.5 МБ). Отдаются по `/api/images/<id>.png` с вечным кэшем:
при замене появляется новая картинка с новым id, старая удаляется.

### Картинки карт

Драфт показывает карты плитками с картинками. Чтобы добавить карту,
положите файл в `frontend/public/maps/` с именем карты в нижнем регистре
без пробелов — например, `mirage.png` для карты «Mirage». Код не содержит
списка карт: если файла нет, плитка просто отрисуется без картинки.

## Локальная разработка

Локально вместо Postgres — SQLite-файл `backend/data/app.db`, создаётся сам.

```bash
# backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cd backend && uvicorn app.main:app --reload

# frontend (в другом терминале)
cd frontend
npm install
npm run dev   # http://localhost:5173, /api проксируется на :8000
```

## Миграции

Схема базы ведётся через Alembic (`backend/alembic/versions/`). **Применять
миграции руками не нужно**: приложение само доводит базу до последней версии
при старте — и локально, и на Vercel после деплоя.

Поменять схему (добавить колонку, таблицу и т. п.):

1. Поправить модель в `backend/app/models.py`.
2. Запустить приложение локально хотя бы раз, чтобы локальная база была на
   последней версии, и сгенерировать миграцию:
   ```bash
   cd backend
   alembic revision --autogenerate -m "что поменялось"
   ```
3. Проверить созданный файл в `backend/alembic/versions/` (autogenerate
   иногда ошибается — например, переименование видит как удаление и
   добавление колонки) и закоммитить вместе с моделью.

После пуша в `main` миграция применится к боевой базе сама. Если она упадёт,
база останется как была (миграция идёт одной транзакцией), а сайт не
поднимется — смотрите логи деплоя на Vercel.

`alembic check` покажет, есть ли в моделях изменения, под которые ещё нет
миграции.
